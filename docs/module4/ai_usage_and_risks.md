# Использование ИИ и оценка рисков

## 1. Цель применения ИИ

В ходе практической работы ИИ использовался как вспомогательный инструмент разработки.

Основные направления применения:

- анализ замечаний статических анализаторов;
- поиск вариантов исправления проблем;
- предложение рефакторинга;
- помощь в определении сценариев тестирования;
- анализ потенциальных рисков предлагаемых изменений.

ИИ не рассматривался как источник гарантированно корректного кода. Все существенные изменения требовали проверки разработчиком.

## 2. Работа с Vue-компонентами

В качестве примеров компонентного тестирования рассматривались:

- `StatusBadge.test.js`;
- `AppPagination.test.js`.

Они проверяют два разных элемента интерфейса: отображение статусов и управление пагинацией.

Эти примеры позволяют рассмотреть применение ИИ при анализе тестового покрытия компонентов и поиске недостаточно проверенных сценариев.

По результатам покрытия:

- `StatusBadge.vue` имеет 100% покрытия строк, ветвей и функций;
- `AppPagination.vue` имеет 100% покрытия строк и функций, 91,66% покрытия ветвей.

Это показывает, что даже при полном покрытии строк и функций могут оставаться непроверенные логические ветви.

При использовании ИИ для разработки подобных тестов важно проверять не только успешное отображение компонента, но и различные входные параметры, граничные значения и пользовательские действия.

## 3. Пример применения ИИ при рефакторинге

### Проблема

В `fetchAll.js` статический анализатор SonarQube обнаружил предупреждение S9382, связанное с использованием `await` внутри цикла. Исходная реализация загружала страницы последовательно.

### Рассматривавшееся решение

В ходе анализа и рефакторинга рассматривался следующий подход:

1. Загрузить первую страницу отдельно.
2. Сформировать список оставшихся страниц.
3. Выполнять их загрузку параллельно.
4. Ограничить количество одновременных запросов.
5. Объединить полученные результаты.

Для ограничения параллельности была выбрана библиотека `p-limit` с максимальным количеством одновременных запросов, равным пяти.

### Проверка результата

При реализации учитывались следующие условия:

- сохранение параметров исходного запроса;
- корректное получение первой страницы;
- сохранение порядка результатов;
- ограничение параллельности;
- обработка ошибок запросов.

После доработки были исправлены тесты функции `fetchAll`, включая проверку ограничения параллельных запросов.

Изменение прошло проверку и было включено в `main` через Pull Request №14.

## 4. Риски использования ИИ

| Риск                                      | Возможные последствия               | Способ снижения                                   |
| ----------------------------------------- | ----------------------------------- | ------------------------------------------------- |
| Некорректная генерация кода               | Ошибки в логике приложения          | Ручная проверка и запуск тестов                   |
| Неполные тестовые сценарии                | Ложное ощущение надёжности          | Анализ граничных случаев и покрытия               |
| Неоптимальный рефакторинг                 | Ухудшение производительности        | Проверка поведения и ограничений                  |
| Изменение исходного поведения             | Регрессии                           | Сравнение результатов до и после изменений        |

| Избыточное доверие ИИ                     | Попадание ошибок в основную ветку   | Code Review и автоматические проверки             |

## 5. Ограничения ИИ

ИИ может предложить синтаксически корректное решение, которое при этом не соответствует архитектуре проекта или реальным требованиям backend.

Также ИИ не всегда учитывает ограничения внешних сервисов, нагрузку на сервер и особенности конкурентного выполнения запросов.

Примером такого риска является параллельная загрузка страниц в `fetchAll`: неограниченное количество одновременных запросов могло бы увеличить нагрузку на backend. Поэтому при рефакторинге был установлен лимит в пять параллельных запросов.

Кроме того, сгенерированные тесты не гарантируют полного покрытия всех возможных состояний программы. Их необходимо сопоставлять с требованиями и реальным поведением компонентов.

## 6. Итог

ИИ оказался полезен при анализе проблем, поиске вариантов исправления и планировании тестирования.

Однако окончательные решения принимались с учётом архитектуры проекта и результатов автоматических проверок.

Практическая работа показала, что наиболее эффективная модель применения ИИ — использование его как помощника разработчика, а не как замены статического анализа, тестирования и ручной проверки кода.
