# 7. Ход разработки

## С чего начиналась работа

Исходные материалы:

1. **Документация проекта** (репозиторий организации `.github`):
   функциональные и нефункциональные требования, ADR-001 о модульном монолите,
   BPMN-схемы процесса «как есть» и «как должно быть», ER-диаграмма базы данных.
2. **Backend** (`ai-buyer-backend`): код на Spring Boot, миграции базы данных,
   описание реализованных модулей.

Главное правило: **делать только то, что описано в документации и поддерживается backend**,
ничего не придумывать сверху.

## Анализ: что умеет backend

Из кода контроллеров (`AuthController.java`, `CatalogController.java`) был составлен список эндпоинтов:

| Модуль | Эндпоинты |
| --- | --- |
| Авторизация | `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `GET /auth/me`, `GET /companies/current` |
| Товары | `GET /products`, `POST /products`, `GET/PATCH/DELETE /products/{id}` |
| Остатки | `GET /inventory`, `GET/PUT /products/{id}/inventory` |
| Продажи | `GET /sales`, `GET /sales/summary`, `PUT /products/{id}/sales/{date}` |

И отдельно — класс `RecommendationCalculator` без REST-метода.

В требованиях есть, но в backend **нет**: поставщики, CSV-импорт, закупки.
Эти разделы во frontend не делались, чтобы не рисовать неработающие экраны.

## Принятые решения и почему

### Vue 3 + Vue Router + Axios
Этот стек указан в описании проекта (README организации). `<script setup>` выбран как
самый короткий и современный способ писать компоненты.

### Без UI-библиотек и без TypeScript
Обычный CSS и JavaScript — меньше новых понятий, код проще читать начинающему.
Дизайн минималистичный: светлый фон, белые карточки, один акцентный цвет (индиго),
цвета состояний — красный, жёлтый, зелёный, серый.

### Без Pinia
Глобальное состояние только одно — авторизация. Для этого хватило `reactive()`
в отдельном модуле. Добавлять ради этого целую библиотеку избыточно.

### Proxy в Vite вместо CORS
Backend не настраивает CORS, и браузер заблокировал бы запросы с порта 5173 на 8080.
Proxy в dev-сервере решает это без изменений в backend. В production эту роль выполняет Nginx.

### Формула рекомендаций на клиенте
Без неё дашборд и рекомендации (FR-08 – FR-11, FR-13) было бы не показать.
Формула перенесена из backend без изменений и проверена на примерах вручную.
В README и в коде отмечено, что это временное решение.

### Запросы вынесены в `src/api/`
Компоненты не знают адресов API. Если на backend что-то поменяется, правится одно место.

### Отправка только изменённых полей в PATCH
Backend различает «поле не передано» и «поле = null». Отправляя только изменения,
мы не перезаписываем лишнего, а пустая категория (`null`) явно её удаляет.

## Проблемы, которые встретились

### Пустые параметры запроса
Backend отвечает `400 BAD_REQUEST` на `?q=` (пустое значение). Решение — функция
`withoutEmpty()`, которая убирает пустые параметры перед отправкой.

### Названия товаров на странице остатков
`GET /inventory` возвращает только `productId`. Пришлось отдельно загрузить справочник
товаров (`fetchAll(getProducts)`) и подставлять название по id.

### Версия для записи продаж
Для `PUT /products/{id}/sales/{date}` нужна `version`, но заранее неизвестно,
есть ли запись за этот день. Решение — сначала найти её (`findSale`) запросом
`GET /sales` с периодом в один день.

### Даты и часовые пояса
Backend проверяет «дата не в будущем» по UTC. Москва — это UTC+3: с 00:00 до 03:00
по Москве уже наступило новое число, а по UTC ещё нет. Если подставить «сегодня» по
местному времени, backend посчитает дату будущей и вернёт ошибку. Поэтому
`src/utils/dates.js` считает даты в UTC.

### Страница не открывалась по localhost
Vite слушал только IPv6-адрес `::1`, а браузер обращался к `127.0.0.1`.
Решение — явно указать `host: '127.0.0.1'` в `vite.config.js`. Заодно добавлен
`strictPort: true`, чтобы при занятом порте Vite не переезжал молча на другой.

## Как проверялась работа

- Сборка `npm run build` после каждого этапа — проверка, что нет ошибок компиляции.
- Формула рекомендаций сверена с ручным расчётом по коду backend на нескольких примерах.
- Запуск с настоящим backend и PostgreSQL в Docker, заполнение демо-данными
  (`npm run seed`), проверка, что страницы открываются, а вход через proxy возвращает токен.
- Ручной проход по всем страницам в браузере по сценарию из README
  (раздел «Как пройти по приложению») — его стоит повторить перед защитой.

## Что можно сделать дальше

Когда backend добавит соответствующие модули:

1. Поставщики (FR-06): список, условия (цена, срок, минимальная партия), выбор поставщика у товара.
2. Закупки (FR-12): создание из рекомендации, позиции, итоговая стоимость, статусы
   `DRAFT → CREATED → ORDERED → RECEIVED / CANCELLED`.
3. CSV-импорт (FR-07): загрузка файла и отчёт «добавлено / обновлено / ошибок».
4. Заменить клиентский расчёт рекомендаций на запрос к backend.
5. Показать бюджет на дашборде (когда появятся цены).
