# 1. Обзор проекта

## Что это за система

**AI Закупщик** — SaaS-система для автоматизации закупок. Бизнес заносит в неё товары,
остатки на складе и продажи, а система считает, какие товары скоро закончатся
и сколько их нужно докупить.

Цель — чтобы сотрудник не считал закупки вручную в Excel, а сразу видел список
«что купить и почему».

## Из чего состоит система

```text
  Пользователь (браузер)
          │
          ▼
  ┌───────────────────┐
  │  Frontend (Vue 3) │   ← этот репозиторий
  └─────────┬─────────┘
            │ REST API (JSON по HTTP), JWT в заголовке
            ▼
  ┌───────────────────┐
  │ Backend (Java 21, │
  │   Spring Boot)    │
  └─────────┬─────────┘
            │ SQL
            ▼
  ┌───────────────────┐
  │    PostgreSQL     │
  └───────────────────┘
```

- **Frontend** — то, что видит пользователь. Он ничего не хранит у себя (кроме токена входа),
  все данные берёт у backend и отправляет обратно.
- **Backend** — бизнес-логика, проверка данных, авторизация. Архитектура — модульный монолит
  (одно Spring Boot приложение, разделённое на модули). Решение описано в ADR-001.
- **PostgreSQL** — база данных.

## Что такое REST API простыми словами

Frontend и backend «разговаривают» HTTP-запросами. Каждый запрос — это:

- **метод** — что сделать: `GET` получить, `POST` создать, `PUT` заменить, `PATCH` изменить часть, `DELETE` удалить;
- **адрес** — с чем: `/api/v1/products/5` — товар с id 5;
- **тело** — данные в формате JSON (для POST, PUT, PATCH).

Пример: создать товар.

```http
POST /api/v1/products
Authorization: Bearer eyJhbGciOi...
Content-Type: application/json

{ "sku": "MILK-1", "name": "Молоко 1л", "category": "Молочка" }
```

Ответ — созданный товар в JSON и код `201 Created`.

Коды ответа, которые встречаются в проекте:

| Код | Значение |
| --- | --- |
| 200 | Всё хорошо |
| 201 | Создано |
| 204 | Выполнено, тела ответа нет (например, удаление) |
| 400 | Некорректный запрос |
| 401 | Не авторизован (нет токена или он истёк) |
| 404 | Не найдено |
| 409 | Конфликт (SKU занят, данные уже изменили) |
| 422 | Данные не прошли проверку |
| 429 | Слишком много попыток входа |

## Что реализовано во frontend

Сделано всё, что сейчас умеет backend, плюс аналитика по формуле из backend:

- регистрация, вход, выход, профиль (требование FR-01);
- товары: список, поиск, фильтр, сортировка, создание, редактирование, удаление (FR-03);
- остатки на складе (FR-04);
- продажи и сводка за период (FR-05);
- анализ, состояния товаров, рекомендации, объяснения, дашборд (FR-08 – FR-11, FR-13).

Не сделано, потому что backend этого пока не умеет: поставщики (FR-06), CSV-импорт (FR-07),
закупки (FR-12).

## Требования, которые выполняет frontend

Кроме функциональных, frontend закрывает и часть нефункциональных требований:

- **NFR-USA-01** — все разделы доступны из единого бокового меню;
- **NFR-USA-04** — у каждой рекомендации есть текстовое объяснение;
- **NFR-USA-05** — пользователь видит понятные сообщения об ошибках, без технических деталей
  (коды ошибок переводятся в текст в `src/utils/errors.js`);
- **NFR-SEC-03** — авторизация через JWT.
